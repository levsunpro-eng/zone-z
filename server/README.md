# Сервис лобби и подбора игроков ZoneZ

Python 3.9 или новее, внешние библиотеки не нужны. Это исходники сервиса; публичный сервер автоматически не развёрнут. Для приглашений через интернет всем игрокам нужен один доступный сервер. Проброс порта на компьютерах игроков не нужен: игровой трафик проходит через сервис.

Для этого проекта выбран бесплатный [Oracle Always Free](../docs/ORACLE.md): Ubuntu 24.04, установщик в `oracle/`, сертификат на публичный IP и автоматическое обновление. Регистрация аккаунта и создание реальной VM ещё нужны. Платный [вариант Fly.io с адресом и TLS](FLY.md) остаётся альтернативой.

Локальная проверка:

```powershell
python server/lobby_server.py
python -m unittest discover -s server -p "test_*.py" -v
```

Адрес по умолчанию: `127.0.0.1:7780`, без TLS. Для отдельного компьютера в локальной сети:

```powershell
python server/lobby_server.py --host 0.0.0.0 --allow-plaintext
```

Для публичного сервера используйте DNS-имя либо IP и доверенный сертификат именно для выбранного имени или IP. Например, на выбранном сервере:

```sh
python3 server/lobby_server.py --host 0.0.0.0 --port 7780 --cert /etc/zonez/fullchain.pem --key /etc/zonez/privkey.pem
```

Разрешите входящий TCP 7780 в межсетевом экране сервера. Клиенты подключаются с TLS, проверяют имя и доверие сертификата. TLS завершается непосредственно в Python; HTTP-прокси без поддержки TCP этот протокол не обслужит. Закрытый ключ хранится только на сервере. Для постоянной работы процесс нужно запускать под менеджером служб выбранного хостинга.

### Вариант Docker Compose

В комплекте есть `Dockerfile` и `compose.yaml`. На выбранном сервере задайте каталог с файлами `fullchain.pem` и `privkey.pem` и запустите из каталога `server`:

```sh
export ZONEZ_TLS_DIR=/etc/zonez
docker compose up -d --build
docker compose logs --tail=100
```

Каталог сертификата монтируется только для чтения. Процесс работает с UID/GID `10001`; выдайте этой группе право чтения ключа без доступа остальных пользователей. Если сертификаты в каталоге являются символическими ссылками, смонтируйте также их цели либо подготовьте отдельный каталог с копиями сертификата и ключа. После обновления сертификата обновите файлы и перезапустите контейнер. Контейнер имеет лимит памяти 1 GiB; нагрузку и реальное потребление памяти следует проверить перед увеличением количества подключений.

### Вариант systemd

Файл `zonez-lobby.service` рассчитан на исходники в `/opt/zonez/server`, отдельного системного пользователя `zonez` и сертификаты в `/etc/zonez`. Создайте пользователя на сервере, предоставьте группе `zonez` чтение ключа (`root:zonez`, режим `0640`), скопируйте unit в `/etc/systemd/system`, затем:

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now zonez-lobby
sudo journalctl -u zonez-lobby -n 100
```

После обновления сертификата: `sudo systemctl reload zonez-lobby`. SIGHUP меняет сертификат для новых соединений, сохраняя установленные связи и лобби; при неверной паре сертификата и ключа прежняя остаётся активной. Эти команды — инструкция для выбранного вами хостинга; данный проект сам не создаёт облачный сервер, DNS-записи или сертификаты.

Сервис подбирает две реальные группы одного режима и версии. Командные группы остаются вместе: первая получает команду 0, вторая — 1. В Deathmatch суммарно не больше 20 человек, и у каждого своя команда. Одна ожидающая группа остаётся в поиске; боты не выдаются за найденных людей. Отдельное действие `bots` запускает тренировку своей группы с признаком `bots: true`.

Максимум 12 друзей в командном лобби и 20 в Deathmatch; для поиска Deathmatch нужно оставить место хотя бы одному сопернику. Лидер первого найденного лобби становится игровым хостом. Сервис пересылает игровые сообщения, а симуляцию считает клиент-хост. При его уходе матч завершается; миграции хоста и отдельного авторитетного игрового сервера пока нет. Лобби не привязаны к аккаунтам: код приглашения даёт доступ к комнате, а имя задаёт сам игрок. Коды приглашений и матчи хранятся в памяти процесса и исчезают при перезапуске.

## Протокол 1

Каждый пакет: 4 байта длины **little endian**, затем UTF-8 JSON. Максимум 512 KiB на JSON. Клиент отправляет `{"service":"ping"}` каждые 20 секунд и получает `pong`. Подключение без входящих пакетов закрывается через 90 секунд. Одна связь обслуживает лобби, поиск и игру.

Сразу после подключения сервер отправляет `{"service":"welcome","id":1,"protocol":1}`. Положительный `id` уникален в процессе сервера; он не является постоянным идентификатором аккаунта.

Клиентские команды:

| Команда | Поля |
| --- | --- |
| `create` | `name` (1–24 символа), `mode` (`team`/`deathmatch`), `version` (1–128 символов) |
| `join` | `code` (8 символов, регистр не важен), `name`, `version` |
| `search` | Только лидер; необязательное булево `searching`, по умолчанию `true` |
| `cancel` | Только лидер; остановить поиск |
| `bots` | Только лидер; явная тренировка своей группы |
| `leave` | Выйти из лобби/матча, ответ `left` |
| `ping` | Проверка соединения, ответ `pong` |
| `game` | `peer` (число), `payload` (строка с JSON игрового сообщения) |

Обновление лобби каждому участнику:

```json
{"service":"lobby","code":"ABCDE234","leader":1,"selfId":2,"mode":"team","version":"build-1","searching":false,"players":[{"id":1,"name":"Host","team":0},{"id":2,"name":"Friend","team":0}]}
```

Во время поиска присоединение закрыто: лидер сначала отменяет поиск. Уход участника отменяет поиск группы; при уходе лидера его роль получает первый оставшийся участник.

При найденном матче или явной тренировке:

```json
{"service":"start","role":"client","peerId":2,"leader":1,"code":"MATCH234","mode":"team","version":"build-1","bots":false,"players":[{"id":1,"name":"Host","team":0},{"id":2,"name":"Opponent","team":1}]}
```

`peerId` — собственный глобальный id игрока. `leader` — id игрового хоста. `code` — общий код нового матча; он заменяет прежний код лобби. Все получают `start` до любого `game` для этого матча. Хост создаёт игровые peer-записи для всех участников, кроме себя; клиенты затем присылают игровое hello.

Клиент → хост: `{"service":"game","peer":0,"payload":"..."}`. Хост получает тот же пакет с `peer`, равным настоящему id отправителя. Хост → клиент: хост указывает положительный id назначения, а клиент получает `peer:0`. Клиент не может выбрать отправителя или отправить сообщение напрямую другому клиенту; участники посторонних матчей недоступны.

При уходе клиента хост получает `{"service":"peer_left","peer":2,"message":"Player left."}`. При потере хоста остальные получают `{"service":"ended","message":"The match host disconnected."}` и могут создать новое лобби. Ошибки действий имеют вид `{"service":"error","error":"version_mismatch","message":"..."}`. Остальные коды: `invalid_request`, `not_found`, `searching`, `full`.

Ограничения: по умолчанию 256 соединений; очередь отправки на клиента — 128 пакетов или 2 MiB; сообщение — 512 KiB; запись в медленное соединение — 10 секунд; чтение тела — 15 секунд. Ограничитель входящего трафика разрешает 1000 пакетов/секунду и 16 MiB/секунду с коротким удвоенным запасом для всплеска игрового хоста. Клиенты с некорректным кадрированием или превышением лимитов отключаются.
